# Aegra C++ 工程开发规范

| 属性 | 内容 |
| --- | --- |
| 状态 | 强制执行 |
| 版本 | 1.0 |
| 适用范围 | Aegra 全部生产代码、测试代码、构建配置和代码生成器 |
| 语言基线 | C++20 |

本文是 Aegra 的代码合入标准。`必须` 表示硬性要求，`建议` 表示除非有明确理由否则应执行。规则冲突时，安全性、数据完整性、模块边界和可测试性优先。

## 1. 基本原则

1. 生产程序、运行时组件和核心库必须使用 C++ 实现。CMake、CI、代码生成和开发辅助脚本可以使用其领域语言，但不得承载产品业务逻辑。
2. 遵循 RAII、单一职责、接口隔离、依赖倒置、最小权限和最小可见性原则。
3. 优先清晰、正确和可验证的实现，不用隐晦技巧换取未经测量的性能收益。
4. 每个模块只公开稳定且必要的接口；实现细节保持私有。
5. 任何持久化格式、跨进程协议和公开接口都必须显式版本化。
6. 当前产品尚未发布，不实现旧仓库、旧测试文件或试验格式的兼容分支；需要兼容时必须先形成 ADR。
7. 修改行为时同步修改测试和文档。代码、测试和规范必须描述同一个事实。

## 2. 代码规模硬限制

以下限制适用于手写代码；第三方和生成代码不计入，但必须放在明确的 `third_party` 或 `generated` 目录，且禁止手工修改。

| 对象 | 限制 | 处理方式 |
| --- | ---: | --- |
| 普通函数或成员函数 | 最多 60 个逻辑行 | 提取有业务含义的子函数或对象 |
| Lambda | 最多 30 个逻辑行 | 提取命名函数或策略对象 |
| 圈复杂度 | 最多 10 | 拆分分支、状态机或策略 |
| 嵌套深度 | 最多 4 层 | 使用 guard clause、提取函数 |
| 函数参数 | 最多 5 个 | 使用语义明确的参数对象；不要滥用布尔开关 |
| `.cpp` 文件 | 最多 800 个物理行 | 按职责拆分 translation unit |
| `.h/.hpp` 文件 | 最多 500 个物理行 | 拆分接口、DTO 或实现细节 |
| 单个类 | 建议不超过 300 个逻辑行 | 拆分协作者，避免 God Object |

逻辑行不包含空行和纯注释行。不得通过压缩格式、多个语句写一行或宏规避限制。确实无法拆分时，必须在同一变更中提交 ADR，说明原因、风险和后续计划。

## 3. 语言与类型

- 使用 C++20；不得依赖编译器未标准化扩展，Windows Adapter 除外。
- 固定宽度持久化字段使用 `std::uint8_t`、`std::uint32_t`、`std::uint64_t` 等。
- 内存大小和容器索引使用 `std::size_t`；跨格式转换必须检查溢出。
- 表示字节序列时优先使用 `std::span<const std::byte>`、`std::vector<std::byte>` 或语义封装类型。
- 不用裸整数同时表达字节数、扇区数、块号和偏移量；边界处使用命名类型或明确字段名。
- 枚举使用 `enum class`，并显式指定持久化枚举的底层类型和值。
- 不使用 C 风格转换；使用最窄的 C++ cast，并在窄化前验证范围。
- 编译期常量使用 `constexpr`；只读视图优先于复制。

## 4. 所有权与资源管理

- 所有资源必须由 RAII 对象管理，包括文件、句柄、锁、快照、数据库事务、映射内存和 SDK 会话。
- 禁止拥有资源的裸指针。独占所有权使用 `std::unique_ptr`，共享所有权只有在生命周期确实共享时才使用 `std::shared_ptr`。
- 非拥有引用优先使用引用、`std::span`、`std::string_view` 或明确的 observer 类型。
- 禁止手写 `new/delete`、`malloc/free`，底层封装或第三方互操作除外。
- 类遵循 Rule of Zero；需要自定义析构时同时审查复制与移动语义。
- 析构函数、释放函数和取消清理路径不得抛出异常。
- 敏感缓冲区使用可清零封装，释放前主动清除。

## 5. 接口与依赖

- 每个 Target 只声明直接依赖，不依赖链接目录中的偶然产物或构建顺序。
- 头文件直接包含自己使用的声明，不依赖传递 include。
- 公共头文件不得包含不必要的第三方或平台头；可使用 PImpl 隔离重型实现依赖。
- `base`、`contracts` 和 `ports` 不得依赖 Windows、Qt、HTTP、数据库或厂商 SDK。
- `pipeline` 只依赖抽象端口和格式模型，不创建具体 Storage、VSS、PostgreSQL 或虚拟化客户端。
- Adapter 实现 Port；Adapter 之间不得直接引用彼此实现。
- 只有 `apps/*` 作为 Composition Root 选择实现并注入依赖。
- 禁止 Service Locator、可变全局对象和隐藏 Singleton 依赖。
- 跨 DLL、插件或进程边界使用版本化 C ABI 或序列化协议，不暴露 STL、异常、RTTI 对象或厂商类型。
- 公共接口变更必须同时更新消费者、契约测试和相关文档。

## 6. 函数与类设计

- 一个函数只完成一个可命名的动作，并保持单一抽象层次。
- 优先 guard clause，避免深层 `if/else` 嵌套。
- 布尔参数会隐藏语义；使用枚举或选项对象。
- 输入默认不可变；输出通过返回值表达，避免多个输出参数。
- 类必须维护清晰不变量；构造完成后对象应立即可用。
- 接口按能力拆分，不创建“万能 Manager”“万能 Backend”或巨型 Connector。
- 虚函数基类必须有虚析构函数；非多态类默认 `final` 或不暴露继承点。
- 不为未来猜测建立抽象；出现真实的第二个实现或明确边界时再提取接口。

## 7. 错误处理

- 可预期的业务和 I/O 失败使用项目统一的 `Result<T>` 与稳定错误码表达。
- 编程错误使用断言或不可达标记；不得静默转成普通业务失败。
- 异常只用于无法在当前层处理的异常状态，不作为普通控制流。
- 异常不得穿过线程、C ABI、DLL ABI 或进程边界；边界处必须转换为稳定错误。
- 捕获异常时保留原因链和上下文，不使用空 `catch (...)` 吞掉错误。
- 错误信息不得包含密码、密钥、令牌或未脱敏客户数据。
- 写入、提交和发布操作必须定义幂等性、失败原子性与崩溃恢复语义。

## 8. 并发、取消与生命周期

- 并发是显式设计，不通过共享可变全局状态获得。
- 优先任务所有权清晰的线程与执行器；线程必须可停止并在所有退出路径 join。
- 长任务必须接受取消令牌，并在有界时间内响应取消。
- 锁保护的数据和不变量必须写在成员附近；避免持锁执行 I/O、回调或未知代码。
- 多锁场景定义固定加锁顺序，或使用 `std::scoped_lock`。
- 原子变量必须说明内存序意图；没有证明时使用默认顺序保证正确性。
- 跨线程回调不得捕获生命周期不明的裸 `this`。
- Backup/Restore Pipeline 必须具有有界队列和背压，禁止无界缓存数据块。

## 9. 持久化与数据完整性

- 磁盘格式使用固定大小类型、明确字节序、magic、版本、长度和校验值。
- 不将内存结构直接 `reinterpret_cast` 后持久化，除非结构经过 packing、size、endianness 和 ABI 静态断言，并有格式测试。
- 解析外部输入前先验证范围；所有 `offset + size` 计算必须防溢出。
- 解析器必须拒绝截断、重叠、越界、未知关键版本和无效引用。
- 个人版 `.bkf` metadata 的 CBOR Map key 使用固定 `snake_case` text string；整数 key 无效。
- 企业 Recovery Point、Manifest、Pack 和 Chunk Index 的权威数据保存在 Repository；PostgreSQL 只保存控制面数据和可重建投影。
- Commit Object 发布前 Recovery Point 不可见；GC 不得只依赖数据库引用计数。
- 新格式必须有 golden、roundtrip、损坏输入和边界值测试。

## 10. 安全

- 密钥、密码和访问令牌通过 `SecretRef` 或受控凭据解析接口传递，不作为普通字符串持久化。
- 日志、异常、进度事件和 telemetry 禁止输出秘密或客户数据内容。
- 加密只使用经过评审的库和 AEAD 算法，不自行设计加密算法。
- 所有随机 nonce、salt、UUID 和密钥材料使用密码学安全随机源。
- 比较认证值使用常量时间函数。
- 输入路径必须规范化并验证根目录，防止目录穿越、设备路径绕过和符号链接逃逸。
- 外部请求、Job 和 Manifest 先做 schema、权限、租户和资源归属校验。
- 默认最小权限运行；提权必须限制在最小进程和最短时间。

## 11. 性能与可观测性

- 优化前先测量；性能变更必须提供基准或 profiling 证据。
- 数据面避免不必要的大块复制和分配，但不得牺牲所有权清晰度。
- 批量处理 Chunk 查询、对象读取和数据库写入，避免逐块网络往返。
- 每个长任务贯穿 `traceId`、`jobId`，Repository 写入还要包含 transaction 和 recovery point 标识。
- 记录逻辑字节、处理字节、存储字节、吞吐、延迟、重试和去重率。
- 日志使用结构化字段和稳定 message code，不用日志文本充当协议。
- 热路径不得同步写低速日志或执行阻塞 DNS、数据库和对象存储调用。

## 12. 命名、布局与格式

- 类型使用 `PascalCase`，函数和变量使用 `snake_case`，常量使用 `kPascalCase`，宏使用 `AEGRA_UPPER_SNAKE_CASE`。
- 文件名使用 `snake_case.h/.cpp`，目录名使用 `snake_case`。
- 接口可以使用 `IBlockSource` 形式，具体实现表达技术与职责，如 `WindowsVolumeBlockSource`。
- 头文件使用 `#pragma once`；include 顺序为自身头、项目头、第三方头、标准库头。
- 命名空间反映模块，例如 `aegra::base`、`aegra::ports`。
- 生产代码标识符和注释使用英文；面向团队的设计文档可以使用中文。
- 注释解释原因、不变量和风险，不复述代码。
- 使用仓库 `.clang-format`；不得为个人偏好大范围重新格式化无关代码。
- 禁止在公共头中 `using namespace`。

## 13. 构建与依赖管理

- 使用 CMake Presets 生成构建；Windows 编译器固定为 Visual Studio 2026 Insiders。
- Windows 工具链目录为 `C:\Program Files\Microsoft Visual Studio\18\Insiders`。
- 第三方库通过 vcpkg manifest 或统一依赖配置管理，禁止开发机绝对 include/lib 路径。
- 内部模块优先静态库；只有明确的进程、插件、Shell Extension 或故障隔离边界使用 DLL。
- 项目代码启用 `/W4`，CI 对新增警告失败；第三方警告通过 system include 隔离。
- 禁止提交编译产物、缓存、用户级 IDE 文件和秘密配置。
- 必须支持干净构建、并行构建和单 Target 构建。

## 14. 测试与质量门禁

- 新功能必须有测试；Bug 修复必须先添加能复现问题的回归测试。
- 单元测试不得依赖真实云账号、生产数据库、物理磁盘或网络共享。
- Port 必须提供可复用 Contract Test Suite，所有 Adapter 运行同一套契约测试。
- 时间、随机数、凭据、I/O 和进度通过 Port 注入，确保测试确定性。
- 格式解析器和跨进程解码器必须覆盖 fuzz 或属性测试入口。
- 并发代码必须测试取消、超时、重复完成、异常和资源清理。
- 架构检查必须阻止反向依赖、循环依赖、跨模块源码 include 和未声明链接依赖。
- 合入前至少执行受影响 Target 的构建与测试；共享基础模块变更执行全部核心测试。
- 提交前运行格式检查、静态分析、`git diff --check` 和秘密扫描。

## 15. 文档与决策

- 架构边界、持久化格式、安全模型或不可逆选择使用 ADR 记录。
- ADR 至少包含背景、决策、替代方案、后果和验证方法。
- 公共接口写清线程安全、所有权、错误、取消和生命周期约束。
- README 只提供入口；详细规范分别放入 `docs/architecture`、`docs/development`、`docs/format` 和 `docs/adr`。
- TODO 必须关联 issue 或明确责任与触发条件；禁止无上下文 TODO。

## 16. Code Review 检查清单

- [ ] 模块依赖方向正确，没有 Adapter 泄漏到核心层。
- [ ] 所有权、资源释放、取消和异常路径明确。
- [ ] 函数、文件、复杂度、参数和嵌套未超过限制。
- [ ] 整数、范围、偏移和长度计算已检查溢出。
- [ ] 写入流程具有幂等、原子和崩溃恢复语义。
- [ ] 日志和错误不包含秘密或客户数据。
- [ ] 测试覆盖成功、失败、取消、边界和损坏输入。
- [ ] 直接 Target 可独立构建，未依赖偶然链接顺序。
- [ ] 行为、格式或接口变化已同步文档。
- [ ] 没有为未发布旧实现增加兼容代码。

## 17. 例外流程

任何违反硬限制或依赖规则的变更都必须先提交 ADR。ADR 必须给出：无法遵守的具体规则、为什么常规拆分不可行、风险、缓解措施、负责人和消除例外的条件。没有 ADR 的例外不得合入。
